# AI 成本雷达 — 功能说明与路线图

> 状态：**P0 完整日志与 P1 成本归因已实现**
> 生产分支：`custom`

---

## 1. 背景与目标

### 1.1 一句话目标
帮团队发现"**谁在浪费 token**"——把分散在各模型调用里的成本数据收集、归因、可视化，并给出可执行的优化建议。

### 1.2 产品愿景（完整形态）
new-api 本身是所有模型调用（OpenAI / Anthropic / Gemini / Azure / Bedrock 等 40+ 上游）的统一入口，天然能拿到全量调用数据。在此之上叠加一层"成本雷达"：

1. **完整日志**：可查看每次请求/响应的完整内容（含提示词原文）。
2. **多维归因**：自动按 用户 / 功能 / 模型 / prompt 模板 统计成本。
3. **浪费识别**：标出"高成本低价值调用"。
4. **优化建议**：给出 替代模型 / 缓存 / 压缩 prompt 等建议。

### 1.3 现状评估（代码基线）
new-api 现有 `logs` 表已记录调用的**结构化统计字段**，多维归因的"用户/模型"维度几乎现成；但**缺三块能力**：

| 能力 | 现状 | 缺口 |
|------|------|------|
| 完整请求/响应正文（含 prompt） | 仅存统计字段，不存正文 | 需新增正文采集与落库 |
| 按"功能 / prompt 模板"归因 | 无此维度 | 需打标签 / 模板指纹 |
| "高成本低价值"识别 | 无"价值"指标 | 需定义价值口径 + 规则 |
| 优化建议 | 无 | 需分析层（规则或 LLM） |

> 关键事实：现有中继链路读完请求体后**并不持久化正文**；响应是边读边流式返回，也不入库。因此"完整日志含提示词"是整个功能的**地基**，必须先建。

## 3. 本次范围（P0：数据采集层）

### 3.1 范围内（In Scope）
- 新增数据表，记录每次调用的**完整请求体 + 完整响应体**（含 prompt 原文）。
- **文本与媒体分离存储**（详见 4.2）：正文表只存清洗后的可读文本（base64 媒体替换为占位符引用），媒体二进制单独存一张表，保证日志可读性。
- 提供**全局开关**控制是否记录（默认关闭）；不按渠道 / 用户细分，全局一个开关。
- 提供**管理员查询接口**，按 `request_id` 取完整请求/响应（含媒体回看）。
- 提供**过期清理（TTL）**，复用现有日志清理机制（正文表 + 媒体表联动清理）。
- 前端运营设置页新增开关入口（含数据量/隐私提示）。
- **日志页查看入口**：在现有日志页（`features/usage-logs`）的日志详情中新增「查看完整请求/响应」按钮，点击调用查询接口，**弹窗**以 JSON 美化（语法高亮）+ 可滚动方式展示完整请求/响应正文。详见 4.5。

### 3.2 范围外（Out of Scope，后续阶段）
- 按"功能 / prompt 模板"归因聚合（P1）。
- "高成本低价值"打分与"价值"口径定义（P2）。
- 替代模型 / 缓存 / 压缩 prompt 等优化建议（P2/P3）。
- 独立的"成本雷达"前端可视化页面（P3）。

## 4. P0 技术方案概述

> 详细设计在实现阶段补充，这里给评审用的概览。

### 4.1 核心难点
- 请求体可在中央位置统一获取（`common.GetBodyStorage(c)`）。
- **响应体已被流式发往客户端、无法在计费钩子处直接获取** → 需在更外层用 ResponseWriter 包装抄录。

### 4.2 存储设计：文本与媒体分离（核心）

> 参考 Langfuse（媒体占位符 + 对象存储）与 Helicone（正文/元数据分层存储）的业界做法。
> **绝不**对整个 body 按字节盲截——那会把排在媒体后面的 prompt 文本也截掉。
> 本项目采用：**正文文本进库 + 媒体二进制独立表**（方案 B 变体，二进制存 DB 而非对象存储）。

**两张新表：**

`request_details`（正文，可读）：
- `id`、`request_id`（索引，关联 `logs`）、`user_id`、`created_at`（索引，用于 TTL）
- `endpoint`、`model_name`、`channel_id`、`token_id`、`status_code`、`is_stream`
- `request_body` / `response_body`：`text` 类型，存**清洗后**的正文——其中 base64 媒体已被替换为占位符引用 token。
- `request_truncated` / `response_truncated`：兜底截断标记（仅极端超长文本触发）。

`request_media`（媒体二进制，**独立表**）：
- `id`、`request_id`（索引）、`media_id`（占位符引用的目标）、`sha256`（索引，用于去重）
- `mime_type`、`size`、`role`（request / response）
- `data`：二进制列。GORM `[]byte` → **PG `bytea` / MySQL `longblob` / SQLite `blob`**（遵守三库兼容规则）。

> **为什么二进制单独建表 + 用 `bytea`**：
> - `bytea` 是 PG 存 blob 的标准类型；PG 的 TOAST 会把大字段自动压缩并外置到 TOAST 表，不影响主表行存储。
> - **关键约束：查询正文/列表时禁止 `SELECT *` 带出 `data` 列**——只有用户显式查看某条媒体时才单独按 `media_id` 拉 `data`。独立表正是为了让正文查询完全不触碰二进制。
> - 默认关闭 + 仅管理员 + 单条 10MB 上限 + `sha256` 去重，足以控制 DB/备份体积。海量规模再升级对象存储（P1+）。
> - 单条媒体超过大小上限：不存二进制，正文占位符标注 `oversized`。

**媒体清洗器（sanitizer）**：解析请求/响应 JSON，遍历内容把 base64 媒体提取出来：
- 按已知字段路径处理多模态：
  - OpenAI chat：`messages[].content[].image_url.url`（`data:...;base64,`）、`input_audio.data`
  - Claude：`content[].source.data`（`source.type=base64`）
  - Gemini：`contents[].parts[].inlineData.data`
  - 兜底：正则检测"超长 base64-like 字符串"
- 媒体二进制写入 `request_media`（按 `sha256` 去重），原位置替换为占位符引用，便于 UI 回看渲染，示例：

```
[media: image/png · 1.2MB · sha256:ab12cd… · id=<media_id>]
```

这样 `request_details` 里的 prompt 文本结构完整、完全可读；媒体只剩一行短引用，UI 可据 `media_id` 回查 `request_media` inline 渲染原图。

### 4.3 实现要点（不侵入各 channel handler）
1. **两张新表**：`request_details`（正文，`text`）+ `request_media`（二进制，`bytea`/`blob`），按 `request_id` 关联现有 `logs`。
2. **媒体清洗器**：见 4.2，落库前把 base64 媒体外置到 `request_media`，正文留占位符。
3. **全局开关**：仿现有 `LogConsumeEnabled` 模式（`common/constants.go` 全局变量 + `model/option.go` 注册同步），默认 `false`。
4. **捕获中间件**：在 relay 路由组上包装 `c.Writer`（完整实现 `gin.ResponseWriter` + `http.Flusher`，保证 SSE 不被破坏），请求结束后异步落库。
5. **兜底截断**：媒体外置后正文仍超长（极端情况）才截断并标记 `truncated`；正常文本永不被截。
6. **查询接口**：`GET /api/log/detail?request_id=xxx`（正文）+ `GET /api/log/detail/media?media_id=xxx`（媒体二进制，按需）。**两者均在路由上挂 `middleware.AdminAuth()` 强制服务端鉴权**（详见 4.6）。
7. **TTL 清理**：接入现有 `log_cleanup` 系统任务。`service/system_task.go` 在日志清理完成后调用 `DeleteOldRequestDetailBatch`，按相同时间边界清理正文与媒体。

### 4.5 前端：完整请求/响应查看弹窗

**入口**：在日志页 `features/usage-logs` 的日志详情弹窗（`components/dialogs/details-dialog.tsx`）中新增「查看完整请求/响应」按钮。
- **显示条件**：仅当全局开关开启、该 log 有 `request_id`、且当前用户有权限（建议仅管理员）时显示，避免无数据时出现死按钮。

**交互**：
- 点击按钮**懒加载**（点击才请求，不随列表预取）调用 `GET /api/log/detail?request_id=xxx`。
- 在**新弹窗**中展示，复用现有 `@/components/dialog` 的 `Dialog` + `ScrollArea`。
- 请求体 / 响应体用 **Tab 切换**；正文为 JSON 时**美化 + 语法高亮**展示，复用现有 `components/ai-elements/code-block.tsx`（基于 `shiki`）。
- 支持：滚动、复制（复用 `use-copy-to-clipboard`）、加载/错误态（React Query + `handleServerError`）。
- **媒体占位符**：正文中的 `[media: …id=<media_id>]` 占位符可渲染为可点击项，按需拉取 `request_media` 预览（图片 inline，其余下载/提示）。

**展示细节**：
- 大正文性能：弹窗内滚动容器限高；超大正文可折叠/截断提示（与后端 `truncated` 标记呼应）。
- 非 JSON 正文（如 multipart、SSE 原文）按纯文本 `pre` 展示。
- 所有文案走 i18n（`useTranslation`）。

### 4.6 接口鉴权（硬性要求）

> 完整请求/响应正文含用户原始 prompt 与媒体，属敏感数据。**权限必须在服务端强制，前端隐藏按钮只是 UX，不构成安全边界。**

- 新增的查询接口与媒体接口**必须在路由上挂 `middleware.AdminAuth()`**，与现有日志接口（`/api/log` 系列已全部使用 `AdminAuth()`）保持一致。
- 注册位置：现有 `logRoute` 组（`router/api-router.go`），示例：
  - `logRoute.GET("/detail", middleware.AdminAuth(), controller.GetRequestDetail)`
  - `logRoute.GET("/detail/media", middleware.AdminAuth(), controller.GetRequestMedia)`
- **不提供 `/self` 变体**：普通用户无法查看任何完整正文（即使是自己的），P0 仅管理员可访问。
- 控制器内同样校验：即便路由配置变更，控制器也应再次确认管理员身份后才返回正文/媒体（纵深防御）。
- 验收时需**直接用非管理员 token 调接口验证返回 403/无权限**，而非仅检查前端按钮是否隐藏。

## 5. 风险与缓解

| 风险 | 说明 | 缓解 |
|------|------|------|
| 存储膨胀 | 全量存正文，请求量大时增长快 | 默认关闭 + 媒体去重 + TTL 清理 |
| 隐私/合规 | 正文含用户原始 prompt，属敏感数据 | **服务端 `AdminAuth()` 强制鉴权**（非仅前端隐藏）+ 全局开关默认关 |
| 多模态体积 | 图片/音频 base64 极大、且会污染正文可读性 | **媒体二进制外置到 `request_media` 表 + sha256 去重**；正文只留占位符；超大媒体可设上限只存占位符 |
| 二进制跨库兼容 | `bytea`/`longblob`/`blob` 类型差异 | GORM `[]byte` 映射 + 按 DB 分支；三库均验证 |
| 性能 | 抄录响应 + JSON 解析 + 写库 | 异步写库（gopool），不阻塞主链路 |
| SSE 兼容 | 包装 Writer 可能破坏流式 | 完整实现 Flusher，充分测试流式场景 |

## 6. 验收标准（P0）

- [ ] 开关关闭时：行为与现状完全一致，无任何额外写库。
- [ ] 开关开启时：调用的完整请求/响应正确落库，可按 `request_id` 查回。
- [ ] **正文可读性**：含图片/音频的多模态请求，`request_details` 中 prompt 文本完整可读，base64 被替换为占位符引用。
- [ ] **媒体外置**：媒体二进制正确写入 `request_media`，可经 `media_id` 回查；相同 `sha256` 去重生效。
- [ ] 流式（SSE）与非流式请求均能正确抄录响应。
- [ ] 极端超长正文（媒体外置后仍超限）按上限截断并标记。
- [ ] 过期数据可被 TTL 清理（正文表 + 媒体表联动）。
- [ ] SQLite / MySQL / PostgreSQL 三库均可正常迁移与读写（含二进制列类型）。
- [ ] **接口鉴权**：用非管理员 token 直接调用 `/api/log/detail` 与媒体接口返回无权限（403），证明权限在服务端生效，而非仅前端隐藏按钮。
- [ ] 完整正文与媒体仅管理员可访问。
- [ ] 媒体超过大小上限时不存二进制、正文占位符标注 `oversized`；相同 `sha256` 去重生效。
- [ ] **前端查看弹窗**：日志详情中「查看完整请求/响应」按钮在有数据时出现，点击懒加载并以 JSON 美化（高亮）+ 可滚动方式正确展示；请求/响应 Tab 切换、复制、加载/错误态均正常。
